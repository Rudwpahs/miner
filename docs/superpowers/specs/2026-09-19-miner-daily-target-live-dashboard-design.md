# Miner Daily Target + Live Dashboard Design

Date: 2026-09-19
Repository: `Rudwpahs/miner`
Related private data repository: `Rudwpahs/hoopDB`

## 1. Goal

Build two connected capabilities without exposing private candidate data:

1. Raise Miner collection capacity so the system targets an average of **1,659 newly exported candidates per Seoul calendar day**.
2. Provide a public, mobile-friendly live dashboard showing aggregate counts for collected data, distillation backlog, and successfully distilled data.

The value `1,659` must not be hard-coded into workflow logic. It must live in one configuration file so it can be changed quickly in response to a plain-language request such as “마이너 하루 2000개로 바꿔”.

## 2. Existing System

Current Miner behavior:

- Public collector repository: `Rudwpahs/miner`.
- Private candidate store: `Rudwpahs/hoopDB`.
- Scheduled collection workflow: `.github/workflows/mine.yml`.
- Current collection schedule: every 3 hours.
- Miner currently uses Crossref plus YouTube RSS adapters.
- Crossref candidates are relevance-checked, DOI identity-checked, deduplicated, then exported to private `hoopDB`.
- Current V3 preparation workflow runs hourly and creates/advances deterministic V3 shadow state.

Private candidate payloads must remain private. The public repository must never receive candidate titles, URLs, authors, summaries, candidate IDs, or raw queue payloads merely to power the dashboard.

## 3. Daily Target Control

### 3.1 Configuration

Create one public configuration file:

`config/miner_target.json`

Initial content:

```json
{
  "daily_target": 1659,
  "timezone": "Asia/Seoul"
}
```

`daily_target` is the single operator-facing knob. The implementation must not duplicate `1659` in workflow shell, Python defaults, dashboard JavaScript, or tests except where a test fixture explicitly proves the configured value is loaded.

### 3.2 Schedule

Change the Miner schedule from every 3 hours to every 20 minutes.

The higher wake-up frequency is for recovery and quota control, not to force a full mining run every 20 minutes.

### 3.3 Quota behavior

At the start of a scheduled run:

1. Resolve the current date in `Asia/Seoul`.
2. Read `daily_target` from `config/miner_target.json`.
3. Read today’s aggregate exported count from safe public state generated by prior runs, or from a server-side aggregate of the private target when rebuilding state.
4. Calculate:

   `remaining = max(0, daily_target - exported_today)`

5. If `remaining == 0`, exit before source API calls.
6. Otherwise mine with a bounded budget and stop exporting once today’s quota has been reached.

A run must never intentionally overshoot the configured target because of batch size. If a fetched batch contains more eligible candidates than the remaining quota, export only the first `remaining` candidates in deterministic order and persist state consistently.

### 3.4 Recovery behavior

- A source rate limit or transient failure must not reset the day’s count.
- The next scheduled run resumes against the same daily target.
- At Seoul midnight, the daily counter starts a new date.
- Existing global deduplication and DOI identity verification remain unchanged.
- Manual dry-runs do not consume the daily export quota.

### 3.5 Capacity expectation

The target is a quota, not a guarantee that upstream sources will always yield exactly 1,659 eligible unique candidates. The dashboard must distinguish:

- target reached,
- still collecting,
- source-limited / error state.

## 4. Public Aggregate Status Contract

### 4.1 Public-only aggregate payload

Generate a small public file such as:

`public/status.json`

Allowed fields:

```json
{
  "schema_version": 1,
  "generated_at": "2026-09-19T18:00:00+09:00",
  "timezone": "Asia/Seoul",
  "daily_target": 1659,
  "collected_total": 0,
  "distillation_pending": 0,
  "distillation_success": 0,
  "today_collected": 0,
  "last_miner_run_at": null,
  "last_distillation_success_at": null,
  "system_status": "COLLECTING",
  "history_7d": [
    {"date": "2026-09-19", "collected": 0}
  ]
}
```

Forbidden public fields include:

- candidate title
- URL or DOI
- author
- abstract/summary
- candidate ID
- canonical hash/fingerprint
- queue batch IDs
- knowledge-unit text
- private repository paths that reveal candidate identity

### 4.2 Metric definitions

`collected_total`
: Count of unique candidate records accepted into the private inbox after Miner deduplication/export.

`distillation_pending`
: Count of candidate states that still require semantic processing to reach a terminal/promoted state. The counter must be derived from the authoritative V3 ledger/state rather than from raw queue-file count alone.

`distillation_success`
: Count of candidates that reached the project’s durable successful terminal state (canonical/promoted/confirmed according to the final V3 materialization rules). It must not count intermediate `PROPOSE_ACCEPT` as success.

`today_collected`
: Unique exports attributed to the current Seoul date.

The aggregation implementation must document the exact ledger/status values used for `pending` and `success` so future V3 changes do not silently change dashboard semantics.

## 5. Aggregation Architecture

Use a one-way data boundary:

`hoopDB (private)` → server-side aggregate job → numeric status payload → public Miner dashboard

The browser must never call the private repository API and must never need a GitHub token.

The aggregate job may run in GitHub Actions with the existing private-repository access token. It reads only what it needs, reduces the information to numeric/time-series fields, validates the payload against an allowlist schema, and writes only the aggregate payload to the public repository/deployment artifact.

Before publishing, the job must fail closed if unknown fields appear.

## 6. Refresh Strategy

Near-live is sufficient; strict WebSocket real-time is unnecessary.

Refresh triggers:

1. After a Miner export/persist cycle.
2. After V3 prepare/state changes.
3. After semantic distillation state changes where the public aggregator can observe them.
4. A periodic 5-minute reconciliation job to repair missed event-driven updates.

The dashboard itself polls `status.json` periodically with cache-busting and displays the payload generation time so stale data is obvious.

## 7. Dashboard UX

Host a public static page from `Rudwpahs/miner` using GitHub Pages.

Mobile-first layout:

Top row / primary cards:

- 수집 데이터
- 증류 대기
- 증류 성공

Secondary information:

- 오늘 수집: `x / daily_target`
- percentage progress bar
- current system status
- last Miner run
- last successful distillation
- 7-day daily collection chart
- status payload update time

Supported status labels:

- `COLLECTING`
- `TARGET_REACHED`
- `DISTILLING`
- `BLOCKED`
- `DEGRADED`

The UI must not expose private object identifiers in tooltips, URLs, DOM data attributes, or source maps.

## 8. Data Integrity and Privacy

The public aggregation code must use an explicit allowlist, not blacklist filtering.

Validation requirements:

- all numeric counters are integers >= 0
- `today_collected <= daily_target` under normal quota-controlled operation
- history contains dates + numeric counts only
- generated timestamps are ISO-8601
- no unexpected JSON keys
- no candidate-like identifier patterns in public payload
- no URL fields other than optional public dashboard metadata explicitly approved later

If aggregation cannot confidently read authoritative private state, keep the last known good public payload and mark the system `DEGRADED` or `BLOCKED`; never publish guessed counts.

## 9. Testing Strategy

Implementation follows TDD.

### Miner target tests

- config loads `daily_target`
- invalid/non-positive target is rejected
- quota remaining calculation
- zero remaining skips adapters/API calls
- partial final batch exports exactly the remaining count
- manual dry-run does not consume quota
- Seoul date boundary resets daily quota
- global deduplication behavior remains unchanged

### Aggregate tests

- fixture inbox + ledger produces expected totals
- pending count uses authoritative state, not queue-file count
- intermediate `PROPOSE_ACCEPT` is not counted as success
- terminal success status is counted once
- duplicate candidates are not double-counted
- allowlist strips/rejects all private fields
- missing or malformed private state fails closed

### Dashboard tests

- renders the three headline counters
- renders daily target from status payload, not hard-coded value
- handles stale/error payload visibly
- no private identifiers or raw candidate fields appear in built assets

### Workflow contract tests

- Miner scheduled every 20 minutes
- status reconciliation scheduled every 5 minutes
- target read from config file
- no literal `1659` in workflow logic
- public deploy step depends on successful aggregate validation

## 10. Operational Change Procedure

To change the daily Miner target later:

1. Edit only `config/miner_target.json` → `daily_target`.
2. Run target/config contract tests.
3. Commit to `main` after validation.
4. Next scheduled Miner run automatically uses the new target.
5. Dashboard automatically displays the same new target from generated status.

No code or workflow schedule change should be necessary for ordinary target changes.

## 11. Out of Scope

- Exposing candidate-level search publicly.
- Publishing private `hoopDB` files.
- Changing V3 semantic decision policy.
- Increasing semantic distillation spend automatically.
- Replacing DOI identity verification or relevance logic.
- Guaranteeing 1,659 eligible unique candidates when upstream sources cannot supply them.

## 12. Acceptance Criteria

The feature is complete when:

1. Daily target is controlled from a single config value initially set to 1,659.
2. Scheduled Miner wakes every 20 minutes and stops API work once the day target is met.
3. Miner can finish a day at exactly the target without batch overshoot.
4. Public status payload contains only approved aggregate fields.
5. Public dashboard shows total collected, distillation pending, distillation success, today/target, 7-day history, and timestamps.
6. Dashboard updates near-live through event-driven refresh plus 5-minute reconciliation.
7. Raw private candidate data never enters the public repo/page.
8. Tests verify quota, privacy boundary, metrics semantics, and workflow contracts.
9. Changing the target later requires changing only one config value.
